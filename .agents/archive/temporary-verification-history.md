## UI 以外的临时验证

H16 的隔离验证脚本一次组合了三个真实工程流程，且当时完成总结给出了对应结果：

- 翻译修改后只允许两份 JSON 和 `catalog_gen.go` 变化，并用 SHA-256 确认无关未跟踪 Markdown 没被格式化。
- 外层设置 `GOTOOLCHAIN=auto`，检查 recipe 实际仍使用 `local`；在副本提高 Go 要求后，应直接拒绝，不能下载另一套工具链。
- depguard 在根包／子包、源码／外部测试包四种位置，先允许标准库，再分别拒绝 MyGo 根包与 UI 包；记录为 4 个允许探针通过、8 个违规导入被拒绝。

这类材料的价值是检查约束是否真的生效，适合在约束变更时按当前规则重建隔离探针。现有 `justfile` 和 `.golangci.yml` 承接实现，不需要另存一份长期执行清单。

H18 的模拟器验证脚本还保存了原文件哈希、相同输入回放对照、人物／职业／武器修改后的能力、战斗预测和实际扣血检查。H19 的原生脚本覆盖 IME 组合输入、文本与 ROM 撤销、窗口焦点、文件面板取消和关闭交互。本轮只恢复并阅读了这些脚本，未复核其运行结果。它们包含固定游戏、字段、窗口名和坐标，不能直接成为当前动态 ROM 集成模板，也不能从脚本存在推断游戏内验证通过。

## 曾经提炼过工具，仍需保留的教训

10 月 31 日的 H17 已讨论过把临时能力提炼为 `cmd/ui-review`、`cmd/script-audit` 和验证记录包装器；用户同意后，当时总结报告实现完成。发掘基线的受管理源码中没有这些命令，不能把旧提案当作现有工具，也没有证据据此判断它们退出工作区的原因。

随后用户追问“command test 你在测什么东西？”。当时答复承认了两项具体局限：

- 假 Unix socket 服务端只能验证 UI 客户端与预设协议的交互，不能证明真实 MyGo 兼容、页面可操作或进程生命周期正确。
- 测试内部用普通 `go build` 构建子进程，外层 `go test -race` 不会因此检测该子进程的竞争。

H05 的 MyGo 升级记录也明确说明，原生 macOS 菜单的完整撤销／重做自动化未能稳定完成，未计为通过。Tester 中的历史路由通过不能替代这项平台证据。

这些历史限制比原样恢复命令和测试更有参考价值。现行约定允许有界临时复核，长期领域工作流也一直保留；“不新增永久 UI／模拟器测试”有明确的适用范围。
